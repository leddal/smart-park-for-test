## 对照方法

1. **索引**：确定性约 100,000 行，基线只有主键、优化表带实际查询模式复合索引。相同设备/指标/时间窗/排序/限制，先验证结果一致；保留 `EXPLAIN (ANALYZE, BUFFERS)`。不强制规划器选索引。
2. **缓存**：冻结业务输入与模拟，调用实际总览查询和 Redis 缓存服务，区分第一次冷请求与预热后的请求。比较业务字段一致；生成时间/缓存状态等运行元数据需明确剔除理由。EF 命令计数记录实际数据库负载。
3. **分页**：约 10,000 资产，全量查询再取首 20 与服务器只取 20；首屏内容一致但总体请求范围不同，字节统计按实际序列化内容。该对照仅说明首屏必要载荷节省。
4. **预约并发**：容量 10、100 个不同游客，基线在隔离表“读余量后插入”并用屏障构造竞态，优化调用真实 `ReservationService`。这是故障注入，不代表自然发生概率；报告超额/重复/拒绝/最终容量，不给延迟优劣结论。

性能场景预热 10 次、正式采样至少 100 次、基线与优化交错；记录中位数/P95/波动与原始样本，不清宿主机缓存。冷启动与稳态分开描述。随机种子与环境、源码标识、查询/索引写入结果文件。

公式：`下降比例=(基线−优化)/基线×100%`，`倍率=基线/优化`；分母为零则不计算。出现负收益/无显著收益须原样报告。正确性采用超额数/重复数/非法状态数，不混同性能提升或“拦截率”。

#### 索引因果与查询计划

实际查询限定同一设备、`metric-07`、同一时间窗，按采集时间降序/Id 升序取 500 行。索引为 `(device_id, metric_code, collected_at)`，不删除应用索引、不改变规划器设置。

基线采用 Seq Scan，过滤掉 **99,199** 行，shared hit **1,256**；优化由 PostgreSQL 自行选择 Bitmap Index Scan + Bitmap Heap Scan，命中 **801** 行，shared hit **814**。两者仍有 Sort，不能声称索引完全消除了排序。单次 EXPLAIN 的执行时间 **3.656 → 0.433 ms** 与上表包含客户端取结果的重复采样是不同口径，不能混算。

计算示例：`(4.3936−1.2307)/4.3936×100%=71.99%`，`4.3936/1.2307=3.57`。证据实现为 `backend/SmartPark.Benchmarks/Scenarios/TelemetryIndexBenchmarkScenario.cs`，索引定义见 API `Data/ParkDbContext.cs`。

#### 缓存因果与冷热区分

实际调用 `OverviewQueryService` 与 `OverviewCacheService`，输入冻结、模拟停止、TTL 为 10 秒，未增加生产基准接口。第一次冷缓存 **54.7262 ms / 12 条 EF 命令**，不能拿热缓存数字冒充首次请求。

100 次正式缓存读取中，EF 命令为零的**推断命中 100 次、推断未命中 0 次**；基线平均 **12 条**，热缓存平均 **0 条**，本轮正式采样数据库命令总量下降 **100%**。这是 EF interceptor 推断，不是 Redis 原生命中计数，也不意味着长期请求都命中；过 TTL 或业务失效后仍须查库。实现：`Scenarios/OverviewCacheBenchmarkScenario.cs`、API `Features/Overview/OverviewServices.cs`。

#### 分页因果与载荷

实际 UTF-8 JSON 为 **4,080,001 → 8,208 bytes**，下降 **99.80%**；物化行数 **10,000 → 20**。优化包括 Count 查询，并核对首屏与总数。该对照比较取得首屏所需的数据量，两种请求的总体返回范围并不相同，不推导页面帧率或端到端渲染速度。实现：`Scenarios/PagingBenchmarkScenario.cs`、API `AssetsController.List` 与 `ToPageAsync`。

#### 预约并发正确性

容量 10，100 个不同游客同时申请；不安全基线仅存在于隔离 benchmark 表，异步屏障强制所有参与者先读余量再写。

| 指标 | 故障注入基线 | 实际 ReservationService |
|---|---:|---:|
| 成功 / 拒绝 | 100 / 0 | **10 / 90** |
| 有效预约数 | 100 | **10** |
| 场次计数 | 1（丢失更新，与记录不一致） | **10** |
| 超额 / 重复 | 90 / 0 | **0 / 0** |
| 序列化失败拒绝 | 0 | 0 |

生产方案的容量、游客唯一性与场次计数三项不变式均成立。收益是避免超额与计数不一致，不是速度提升；强制竞态不能解释为自然发生概率。实现：`Scenarios/ReservationCorrectnessScenario.cs`、API `Features/Services/ServicesController.cs` 中的 `ReservationService`。
